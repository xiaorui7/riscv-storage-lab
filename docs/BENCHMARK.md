# Block-cache benchmark

## Environment and method

Recorded on 2026-09-30 using Ubuntu 24.04 x86-64 in a Linux development
container on Windows, RISC-V GCC 13.2.0 and QEMU 8.2.2. Guest: `virt`, one CPU,
8 MiB RAM, modern VirtIO MMIO, 8 MiB raw disk generated by `scripts/mkimage.py`.
Kernel uses the repository's debug/default optimization settings (no `-O`).

Run `make benchmark`. The kernel mounts KTFS to validate startup, then each
workload creates its own empty 64-entry / 512-byte cache over the actual VirtIO
endpoint. Each does 1,024 acquire/release read operations. The benchmark does
not use the mock I/O used for cache fault tests, and it does not include file
lookup/syscall overhead. Each run uses a fresh image.

- **Sequential:** eight cycles through blocks 0–127 in ascending order.
- **Hot set:** 128 cycles through blocks 0–7.
- **Random:** blocks 0–127 using 32-bit xorshift (13, 17, 5), seed `0x391`,
  one generator update per read and block index `state % 128`.

Counters start at zero for every workload. Hit rate = hits / operations.
No wall-clock throughput or latency is claimed.

## Actual results

| Workload | Operations | Hits | Misses | Evictions | Backing reads | Backing writes | Hit rate |
|---|---:|---:|---:|---:|---:|---:|---:|
| Sequential | 1,024 | 0 | 1,024 | 960 | 1,024 | 0 | 0.00% |
| Hot set | 1,024 | 1,016 | 8 | 0 | 8 | 0 | 99.22% |
| Random | 1,024 | 497 | 527 | 463 | 527 | 0 | 48.54% |

Raw kernel rows:

```text
BENCH sequential 1024 0 1024 960 1024 0
BENCH hot_set 1024 1016 8 0 8 0
BENCH random 1024 497 527 463 527 0
```

Columns after the workload name are operations, hits, misses, evictions,
backing reads and backing writes. Current runs write `build/benchmark.log` and
`build/benchmark.json`; the validated snapshot is in `docs/evidence/`.

## Interpretation

The sequential working set is twice the cache capacity, so each block is
evicted before its next visit. The hot set fits entirely; only its eight initial
loads miss. The seeded random workload revisits some resident blocks and misses
on others. Its 48.54% hit rate is a result for this finite trace, not a universal
property of random workloads.

All workloads are read-only, so writes are zero. Evictions exclude initial
empty-slot fills. There are no injected I/O errors in these benchmark runs, so
misses equal backing read calls. In failure tests this equality need not hold.

## Limits

This measures cache behavior in an educational kernel, not production storage
performance. QEMU scheduling, virtualization and the host page cache can distort
timing; backing-device calls are not physical-disk reads. There is no comparison
against a pre-upgrade performance baseline and no measured speedup claim.
The suite does not assess concurrent workload scaling, write-heavy workloads,
crash recovery or stable-media durability.
